## 问题

中文在 Tokenizer 层面有什么坑？实际做应用时会踩到哪些问题？

## 核心答案

1. **切分不稳定**：中文没有空格边界，BPE 从字节/字符开始合并，同一个词在不同上下文可能被切成不同子词组合（"购买"有时是 1 个 token，有时拆成"购"+"买"），语义一致性不如英文；
2. **更费 token**：主流词表以英文为主，同样一段话中文通常消耗更多 token——直接推高 API 成本、窗口占用与延迟；
3. **数字被切碎**：大数字逐位拆分（如"1234567"拆成多个 token），是模型算术不稳的诱因之一；
4. **专有名词/成语/行业术语切分抖动**，影响 RAG 关键词匹配与模型对术语的理解一致性；
5. **全半角标点、简繁体、中英混排**都会产生 token 形态差异。

## 深度解析

- 加分点：国产模型（Qwen、DeepSeek 等）普遍扩充中文词表，中文压缩率明显更好——这也是"中文业务选国产模型"的一个实际理由（呼应模型选型题）；
- 应用侧对策：RAG 的 query 与文档用同一 tokenizer 口径评估成本与匹配；关键数字在 Prompt 中做保护（如加空格/重述）；成本核算必须用真实中文文本实测，不要按英文字符比例估；
- 雷区：按"1 个汉字 = 1 个 token"粗算成本——实际 1~2 个不等，且不同模型词表差异很大。
