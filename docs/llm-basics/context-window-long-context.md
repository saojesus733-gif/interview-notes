## 问题

什么是上下文窗口？上下文变长会带来哪些问题，如何应对？

## 核心答案

- **上下文窗口**：模型一次能处理的最大 token 数（输入 + 输出共享），决定了「模型能看多长的资料、记多长的对话」。不同模型窗口不同（从几 K 到百万级 token 都有，以具体模型文档为准）。
- **窗口变长的问题**：
  1. **注意力计算 O(n²)**：序列越长，单次前向的计算与显存开销增长越快（KV Cache 也线性膨胀）；
  2. **效果问题**：窗口大 ≠ 用得好，存在「中间信息丢失」（lost in the middle）现象——关键信息放在超长上下文中间位置时，利用率明显低于开头和结尾；
  3. **成本与延迟线性/超线性上升**。
- **应对策略**：
  1. 工程侧：RAG 只把最相关内容放进窗口、上下文压缩摘要、多轮对话裁剪（见记忆类题目）；
  2. 模型侧：滑动窗口注意力、稀疏注意力、位置编码外推扩展（RoPE 插值 / NTK）、KV Cache 压缩。

## 深度解析

- 「有效上下文」短于「标称上下文」：评估模型长文本能力要看大海捞针（Needle-in-a-Haystack）类测试在整段长度区间的表现，而非只看标称值。
- 长上下文不是 RAG 的替代品：把海量资料全塞进窗口成本高且中间信息利用率低，实际生产常用「检索缩小范围 + 长窗口兜底」的组合。
- 多轮对话中，窗口预算应优先留给：系统指令、关键事实、与当前问题最相关的内容。
