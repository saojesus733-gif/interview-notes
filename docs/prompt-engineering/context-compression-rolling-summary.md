## 问题

多轮对话或长任务中上下文超出预算怎么办？滚动摘要如何实现？

## 核心答案

**总体思路：先压缩、后裁剪、最后才截断**，尽量保信息、控成本。

**滚动摘要（Rolling Summary）的典型做法**：

1. 设定阈值：当对话历史 token 数超过预算（如窗口的 60%）时触发；
2. 把「较早期的一段对话」交给模型总结成结构化摘要（关键事实、用户偏好、未完成任务）；
3. 用摘要替换原始历史，保留最近 N 轮原文（保证细节精度）；
4. 新一轮对话继续滚动，摘要本身也可随时间再压缩（摘要的摘要）。

```text
[系统提示]
[滚动摘要：用户此前咨询了退款，订单号 X，已确认符合条件……]
[最近 N 轮原文对话]
[当前输入]
```

**其他压缩手段**：

- 工具结果压缩：只保留与任务相关的字段/片段，工具原始返回不进历史；
- 关键信息结构化：把「用户邮箱是 x@y.com」这类事实抽成条目存储，按需注入而非全文保留；
- 分层记忆：久远信息外置到长期记忆库，检索时按需召回。

## 深度解析

- 摘要有信息损耗风险：数字、名称、承诺等「硬信息」必须在摘要中被显式保留，可以做「保护名单」机制（关键实体不压缩）。
- 摘要本身也要花一次 LLM 调用，属于用小成本换主链路成本；高频场景可用小模型做摘要。
- 与 Chat History 的关系：完整历史永远单独持久化（审计/回溯），压缩只发生在「喂给模型的那份上下文」上——两份数据职责分离。
