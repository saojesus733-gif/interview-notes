## 问题

Agent 的记忆应该存在哪里？向量数据库、Redis、关系型数据库各自适合存什么？

## 核心答案

**按记忆的访问模式选存储**：

| 方案 | 适合存 | 访问模式 | 典型场景 |
| --- | --- | --- | --- |
| **向量数据库** | 语义化记忆条目、文档片段 | 相似度检索 Top-K | 「用户之前提过什么偏好」 |
| **Redis** | 会话状态、最近对话、临时上下文 | 按 Key 精确读写、低延迟、TTL | 在线会话的短期记忆缓存、多轮对话热数据 |
| **关系型数据库（MySQL 等）** | 用户画像、事实条目、任务记录 | 结构化查询、事务、精确更新 | 「用户的套餐等级」「订单状态」 |
| **对象存储/文档库** | 原始文档、大文件 | 批量读取 | 知识源文件、归档历史 |

**典型组合架构**：

```text
热层：Redis 存当前会话上下文与最近 N 轮对话（毫秒级读写）
温层：MySQL 存用户画像、长期事实（结构化、可审计）
语义层：向量库存记忆与知识（语义召回）
```

- 读写链路：会话进行中查 Redis → 需要历史/画像查 MySQL → 需要语义记忆查向量库 → 按预算拼进上下文。

## 深度解析

- 不要「只用向量库存一切」：精确事实（手机号、订单号）走语义检索既慢又不可靠，结构化字段必须结构化存；
- Redis 会话数据要设计 TTL 与持久化策略（过期丢会话 vs 开 AOF/RDB），并考虑容量上限；
- 记忆条目建议统一 Schema（内容、类型、时间戳、来源、置信度），跨存储迁移与合并才有据可依。
