## 问题

多轮对话的记忆如何持久化？服务重启、用户隔天再来，会话状态怎么保证不丢？

## 核心答案

**核心原则：会话状态外置存储，服务无状态化。**

**持久化设计**：

1. **会话标识**：每个会话有唯一 session ID，用户设备侧记住它，请求必带；
2. **两级存储**：
   - **热数据**（当前活跃会话的最近上下文）→ Redis，读写快，设 TTL（如 24h 无活动过期）；
   - **冷数据**（完整 Chat History、任务记录）→ 关系型数据库/对象存储，永久归档；
3. **写时机**：每轮对话结束（响应发完后）异步落库；工具调用等关键事件实时写；
4. **恢复路径**：活跃会话从 Redis 读；过期/跨天会话从数据库加载 → 重建上下文（历史摘要 + 最近原文）→ 继续对话。

**关键问题与对策**：

- 并发写：同一会话多请求并发 → 会话级锁或按消息序号合并；
- 消息顺序：记录时间戳与序号，恢复时排序重建；
- 大会话：按阈值滚动归档，恢复时只重建摘要 + 最近窗口。

## 深度解析

- 「无状态服务 + 外置状态」是微服务的基本功，Agent 会话只是把「状态」从 session 对象换成了对话+记忆的复合结构；
- 上下文重建是有损的（KV Cache 丢失、摘要损耗），所以热会话尽量保住 Redis 里的现成上下文；配合推理侧 Prefix Cache，重建成本也能摊薄；
- 隐私合规：对话数据属敏感数据，要分级加密、保留期限与用户删除权（遗忘权）设计。
