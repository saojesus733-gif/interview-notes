## 问题

什么是 Agent 系统中的控制流与数据流？为什么要解耦？图编排框架如何体现这种解耦？

## 核心答案

- **控制流（Control Flow）**：决定「下一步执行哪个节点」——跳转、分支、循环、终止的逻辑。
- **数据流（Data Flow）**：决定「节点之间传递什么数据」——状态如何被读取、更新、合并。

**为什么要解耦**：

1. **各自演进**：业务逻辑变化（改数据处理）不影响流转逻辑（改步骤顺序），反之亦然；
2. **可测试**：节点是「输入状态 → 输出更新」的纯逻辑，可以脱离图单独单测；流转规则也可以单独验证；
3. **可视化与审计**：控制流是图（一眼看懂流程），数据流是状态通道（一眼看懂数据从哪来到哪去）；
4. **并行更容易**：数据流明确后，无依赖的节点可以安全并行（Fan-out），结果按规则合并。

**图编排框架（如 LangGraph）的体现**：

- **Node**：只做数据处理——读 State、执行逻辑（LLM/工具）、返回状态更新；
- **Edge（含条件边）**：只做控制流转——根据当前 State 决定下一个节点；
- **State**：中心化的数据通道，通过 reducer 声明「多路写入如何合并」。

即：节点管「算什么」，边管「接下来去哪」，State 管「数据怎么流动」。

## 深度解析

- 反例是早期 ReAct 文本循环：控制流（下一步做什么）和数据（对话历史）全部搅在一段上下文里，靠模型「自己注意」，难以测试与恢复。
- 解耦后的额外收益：同一份数据流（State 定义）可以挂不同控制流做 A/B 实验；断点恢复只需重放「状态 + 待执行节点」。
- 设计检查法：如果你发现「改一个节点的业务逻辑要连着改跳转逻辑」，说明耦合了，该引入显式的状态通道或条件边。
