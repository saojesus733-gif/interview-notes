## 问题

有种说法是"90% 的生产 Agent 死于无限循环"（Loop of Death）。这个循环是怎么发生的？架构上有哪些防线？

## 核心答案

**发生机制（三个条件叠加）**：

1. **目标感稀释**：长循环里历史动作/失败观察占满上下文，全局目标被淹没——模型"忘了自己要干嘛"；
2. **失败刺激循环**：工具报错回填 → 模型换个姿势重试 → 又失败 → 继续重试；或两个方案来回横跳；
3. **无终止约束**：没有预算上限、没有震荡检测、没有升级路径——循环只会被外部（超时/烧钱告警）打断。

**架构防线（四层，缺一不可）**：

1. **预算硬上限**：最大步数 / token / 费用 / 墙钟时间，任一触发即终止并输出部分结果；
2. **震荡检测器**：识别重复动作指纹（同工具同参数、A→B→A 环），命中后注入纠偏指令或强制终止；
3. **状态化进度**：结构化进度表让模型"看得见走到哪"（对抗目标稀释）；
4. **显式终止与升级**：放弃/转人工/总结部分结论，都是合法出口而不是失败。

## 深度解析

- 关键认知：**这是架构问题，不是 Prompt 问题**——在 Prompt 里写"请不要循环"毫无约束力，护栏必须在代码层；
- 根因治理在上下文工程：工具结果瘦身、失败信息摘要化、进度锚点常驻（呼应 Context Engineering）；
- 雷区：只设 max_steps 不做震荡检测——预算烧光才停，钱照花；把循环归咎于"模型笨"而忽略上下文腐烂。
