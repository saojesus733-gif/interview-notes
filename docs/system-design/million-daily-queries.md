## 问题

一个日均百万级查询的 LLM 问答应用，架构上要注意什么？

## 核心答案

**先做容量换算**：100 万/天 ≈ 平均 12 QPS，按峰值系数 5~10 倍估 60~120 QPS——量级不大，但 LLM 请求「单请求贵、耗时长」，瓶颈在成本与 GPU 并发而非纯 QPS。

**架构要点**：

1. **分层模型路由（最大杠杆）**：简单意图/高频 FAQ 用小模型或规则+缓存；复杂问题才到旗舰模型——多数流量根本不该到大模型；
2. **缓存体系**：高频问题精确缓存 + 相似问题语义缓存，命中率 30% 即砍三成成本；
3. **流式 + 排队**：SSE 输出降低体感延迟；网关按配额排队削峰；
4. **无状态水平扩展**：业务服务无状态随意扩；LLM 调用走统一网关控并发；
5. **降级链路**：主模型故障→备用模型→缓存答案→静态兜底话术；
6. **成本看板**：按请求类型统计 token 与费用，异常放大（如 RAG 塞料过多）及时告警。

**容量 checklist**：

- 每请求 token 预算（输入/输出分开估）× QPS → 每日 token 量 → 费用与配额；
- 峰值并发 × 平均响应时长 → 并发连接数（SSE 长连接要专门算）；
- 检索层：QPS × 检索延迟 → 向量库实例数。

## 深度解析

- 「日均百万」是典型的成本敏感型量级：优化优先级 = 缓存命中 > 模型分级 > Prompt 瘦身 > 推理优化，前者都是纯工程手段，见效快；
- SSE 长连接的连接管理（百万日请求 × 数十秒连接）要求网关连接数与超时参数专门调优，HTTP/2 多路复用可显著缓解；
- 灰度与回归：流量大了之后任何 Prompt/模型变更都要灰度 + 评估集回归，防止「改一处崩全网」。
