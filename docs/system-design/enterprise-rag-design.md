## 问题

设计一个支持高并发的企业级 RAG 系统，你会怎么架构？

## 核心答案

**分层架构**：

```text
接入层：网关（鉴权、限流、租户路由）
服务层：无状态 RAG 服务（可水平扩容）
  ├─ 语义缓存层：query → 答案缓存（命中直接返回）
  ├─ 检索层：混合检索 + Rerank（独立部署，独立扩容）
  └─ 生成层：LLM 调用（走统一网关，多模型路由）
数据层：向量库（分片/副本）+ 对象存储 + 元数据库
异步层：文档摄入管道（解析→切分→Embedding→入库，与在线链路隔离）
```

**高并发关键设计**：

1. **缓存三级**：精确缓存（同问同答）、语义缓存（相似问题命中）、向量缓存（同文本不重算 Embedding）；
2. **检索与生成独立伸缩**：检索层是 CPU/内存密集，生成层是 LLM 延迟，瓶颈不同分开扩；
3. **批处理与并发**：Embedding/重排批量请求；LLM 网关做并发控制与排队；
4. **降级预案**：重排超时→只用召回结果；向量库故障→关键词检索兜底；LLM 不可用→缓存/拒答话术；
5. **多租户隔离**：向量按租户/权限过滤，数据、配额、限流按租户隔离；
6. **流式输出**：SSE 降低首字延迟，改善高并发下的排队体验。

## 深度解析

- 容量估算先行：QPS × 单请求 LLM token 数 → 网关配额与 GPU/配费预算；检索层按 QPS × ANN 查询延迟估算实例数；
- 一致性问题：文档更新后索引有延迟，重要场景设计「增量索引 + 更新通知」，并接受可配置的最终一致窗口；
- 成本大头是 LLM token：缓存命中率与上下文长度控制是两个最优性价比杠杆。
