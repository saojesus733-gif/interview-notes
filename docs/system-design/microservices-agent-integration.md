## 问题

在已有微服务架构中，Agent 系统应该怎么落地？如何与现有服务集成？

## 核心答案

**定位建议：Agent 作为独立微服务（AI 服务层），而不是散落在各业务服务里。**

**参考架构**：

```text
业务前端
  → BFF/网关
      ├→ 常规业务微服务（原有链路不动）
      └→ Agent 服务（会话管理 + 编排 + 工具注册）
              ├→ LLM Gateway（模型调用统一治理）
              ├→ 工具层：封装各业务微服务的 API 为 Agent 工具
              └→ 基础设施：向量库 / 记忆存储 / 工作流引擎
```

**集成要点**：

1. **工具 = 服务化封装**：业务微服务的 API 经工具网关包装成 Agent 工具（鉴权、脱敏、幂等、审计在网关层统一做），业务服务本身不感知 LLM；
2. **权限透传**：Agent 代表用户操作时透传用户身份（on-behalf-of），业务服务按原权限模型校验——Agent 不应拥有超级账号；
3. **契约与降级**：Agent 服务对外提供稳定 API/事件接口；LLM 不可用时业务链路可降级回传统流程（规则/表单），**AI 失败不阻断主业务**；
4. **可观测打通**：trace ID 从业务请求贯穿到 Agent→LLM→工具全链路，一个请求一条完整链路；
5. **独立演进**：Prompt/模型/工具变更在 Agent 服务内灰度发布，不影响业务服务发布节奏。

## 深度解析

- 反模式：把 LLM 调用散进每个微服务——密钥管理、成本核算、评估回归全部失控；
- 数据面与控制面分离：Agent 服务控制编排（控制面），工具调用直接从 Worker 打到业务服务/网关（数据面），避免所有数据都绕经编排层造成瓶颈；
- 团队协作边界：业务团队定义「我能提供什么工具」，AI 团队定义「Agent 怎么用」——工具契约是两个团队的对接口。
