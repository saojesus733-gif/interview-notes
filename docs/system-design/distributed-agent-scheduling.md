## 问题

当 Agent 任务量大、耗时长、需要多机执行时，如何设计分布式 Agent 调度系统？

## 核心答案

**核心思路：执行无状态化 + 状态外置 + 任务队列化。**

**架构**：

```text
任务提交 API → 任务队列（按优先级/租户分队列）
                  ↓
        Worker 集群（拉取/被派发任务）
                  ↓
      Agent 运行时（执行循环 + 工具调用）
                  ↓
状态存储：任务状态库 + 检查点（Redis/DB）+ 事件日志
```

**关键机制**：

1. **任务模型**：任务 = 类型 + 输入 + 预算（时长/token/费用）+ 重试策略；状态机（排队/运行/挂起/成功/失败/取消）；
2. **Worker 无状态**：Worker 从队列领任务，从检查点恢复状态执行——任何 Worker 可挂可扩；
3. **租约与心跳**：Worker 领任务带租约，定期心跳；超时未续 → 任务自动释放回队列（防 Worker 宕机任务卡死）；
4. **幂等**：任务带唯一 ID，重复投递/重试不产生副作用（工具层幂等 key）；
5. **优先级与公平**：高优先级插队，但防饿死（每队列保底配额）；
6. **长任务**：挂起（等人审/等外部回调）不占 Worker，事件到达重新入队；
7. **可观测**：队列深度、任务时长分布、失败率、Worker 负载，慢任务可追踪到检查点级别。

## 深度解析

- 与普通异步任务的区别：Agent 任务的耗时方差极大（10 秒到 1 小时），调度器必须支持「暂停-恢复-取消」的完整生命周期，纯「提交-执行」模型不够；
- LLM 调用是任务的主要成本与瓶颈：Worker 层做并发限流对接网关配额，避免单个大任务独占；
- 有序性要求：同一会话的任务尽量路由到同一处理链（按 session hash），避免并发执行互相覆盖状态。
