## 问题

自旋锁和互斥锁有什么区别，各自适用什么场景？乐观锁、悲观锁又是什么思想，CAS 存在什么问题？

## 核心答案

- **自旋锁**：拿不到锁就原地空转（忙等）不让出 CPU；适合临界区极短、多核的场景，
  避免了睡眠与唤醒的两次上下文切换开销。
- **互斥锁**：拿不到锁就睡眠挂起，让出 CPU 等内核唤醒；适合临界区长、含 IO 的场景；
  单核 CPU 上自旋只会白白浪费时间片，更适合互斥锁。
- 选择口诀：**临界区短用自旋，临界区长用互斥**；混合策略是先自旋有限次数再睡眠（自适应锁）。
- **悲观锁**：假设并发一定冲突，先加锁再操作（互斥锁、数据库 `SELECT ... FOR UPDATE`）。
- **乐观锁**：假设不冲突，直接操作，提交时校验版本号，失败就重试；通常用 **CAS**（比较并交换）实现，是无锁化基础。
- **CAS 的 ABA 问题**：值从 A → B → A，CAS 误以为没变过；
  用版本号/时间戳解决，如 Java 的 AtomicStampedReference。

## 深度解析

- 底层机制：自旋锁靠原子指令（x86 的 lock 前缀指令、CAS）在用户态完成，全程不陷入内核；
  互斥锁竞争失败要陷入内核睡眠，切换成本高，这正是两者适用场景差异的根源。
- ABA 的危害实例：无锁栈中节点被释放又被复用，指针地址相同但对象已不是原来的，
  直接 CAS 会把链表结构改坏，所以共享内存 + 无锁结构必须带版本号。
- 追问点：自旋锁持锁期间不能睡眠——持有者被调度走，其他 CPU 会空转到它回来，实时性反而变差。
- 常见误区：乐观锁不是一种具体的锁，而是「提交时校验」的并发思想，
  对应数据库 MVCC、Redis WATCH、Git 提交等设计。
- 追问延伸：CAS 只能保证单个变量的原子性，多个变量需要用锁或把变量合并成一个对象（AtomicReference）。
