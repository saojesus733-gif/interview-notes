## 问题

面试官问：“线上系统怎么保证一条消息从生产到消费全程不丢？”
要求按生产端、Broker 端、消费端三段分别讲清手段并形成闭环，漏掉 min.insync.replicas 这类细节会显得缺乏实战。

## 核心答案

1. 生产端：设置 acks=all，消息写入所有 ISR 副本才算发送成功；开启 retries 自动重试。
   用带回调的异步发送，失败时记日志、落补偿表或告警，不能发完就不管。
2. Broker 端：副本数 replication.factor >= 3，min.insync.replicas >= 2，保证至少两个副本同步成功才应答。
   Kafka 默认异步刷盘、靠多副本冗余保证持久，同时关闭 unclean.leader.election 防止落后副本当选 Leader 截断数据。
3. 消费端：关闭自动提交位移，改为业务处理成功后手动提交 offset。
   严格做到“先处理、后提交”，处理失败就不提交让消息重投，宁可重复不可丢失。
4. 三端闭环：生产端保证“一定写进 Broker”，Broker 端保证“多副本都落盘”，消费端保证“处理成功才确认”。
   三段各自可靠、串联起来才真正不丢，任何一环偷懒都会前功尽弃。
5. 补充：生产端开启 enable.idempotence 避免重试导致的消息重复与分区内乱序。
   发送最终失败的消息落补偿表由定时任务重发，形成发送侧的最终闭环。
6. 取舍提醒：acks=all 加多副本会拉高发送延迟，一般只对订单、支付等核心链路开启。
   日志、埋点类消息容忍少量丢失，用默认配置换吞吐即可。

## 深度解析

- acks 三档的取舍：acks=0 不等确认最快但可能丢；acks=1 只等 Leader 写入，Leader 宕机且消息未同步时丢失。
  acks=all 配合 min.insync.replicas>=2 才是可靠与性能的平衡点。
- 追问“先处理后提交，处理完还没提交就宕机怎么办”：消息会重复投递，不丢的代价就是可能重复。
  所以不丢消息的方案必须和幂等方案成对出现，这是本题的标准收尾。
- 常见误区：以为开了持久化或刷盘就不丢。若 ISR 收缩到只剩一个副本还在写入，副本全挂仍会丢数据。
  min.insync.replicas 的作用就是限制最小同步副本数，不满足时 Broker 直接拒绝写入。
- 追问扩展：RocketMQ 对应同步刷盘加同步复制，机制不同但“三端各自可靠”的思路完全一致。
- 兜底实践：对资金、订单等核心链路做定时对账（生产记录与消费结果比对），发现丢失自动补偿。
  参数可能配错、机器可能全挂，对账才是最后一道保险。
