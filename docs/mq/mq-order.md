## 问题

面试官问：“下单、支付、发货这类有先后依赖的消息，经过消息队列后怎么保证顺序不乱？”
要求分清全局顺序与分区顺序，并说出 Kafka 从发送端到消费端的完整落地方案。

## 核心答案

1. 全局顺序：整个 Topic 内消息严格 FIFO，RocketMQ 需要把读写队列数设为 1，吞吐极低。
   仅用于 binlog 同步、审计等强依赖全序的场景，一般业务不用。
2. 分区顺序：只保证同一业务键内的消息有序，不同键之间并行，是吞吐与顺序的折中。
   绝大多数业务（同一订单的操作有序）只需要分区顺序。
3. Kafka 发送端：按 key 路由，同一订单 ID 的消息哈希进同一分区，分区内天然 FIFO。
4. 发送端细节：开启重试时若 max.in.flight.requests.per.connection 大于 1 且未开幂等，先发失败后发成功会乱序。
   解决：开启幂等生产者，或把该参数设为 1（牺牲吞吐）。
5. 消费端：一个分区只分给组内一个消费者；消费者内部对该 key 的消息单线程处理。
   多线程时按 key 二次哈希分发到内存队列，同 key 串行、不同 key 并行。
6. 乱序后果：先“发货”后“下单”、先“取消”后“支付”，会造成状态机错乱、资金对不上账。
   设计时要先梳理业务键，明确哪些操作必须有序、哪些可以乱序并行。

## 深度解析

- 全局顺序吞吐差的原因：所有消息挤在一个队列里无法水平扩展，顺序的代价就是并行度。
- 追问“分区扩容会怎样”：分区数变化会改变 key 的哈希落点，扩容瞬间同一 key 的新消息会落到别的分区。
  所以要么固定分区数，要么在业务低峰期变更并短暂暂停生产。
- 消费端多线程的坑：直接对整个分区起线程池，offset 提交可能越过还没处理完的消息。
  标准做法是“按 key 分发内存队列 + 每个队列单线程 + 处理完统一提交”。
- 常见误区：以为配置了顺序就万无一失，消费失败重试同样会破坏顺序。
  失败消息要么阻塞后续（保顺序牺牲可用），要么跳过（保可用牺牲顺序），必须按业务取舍。
- RocketMQ 对比：用 MessageQueueSelector 选队列，消费端用 MessageListenerOrderly 对队列加锁串行消费。
  比 Kafka 的手工方案更开箱即用，面试时可补充这个差异化能力。
