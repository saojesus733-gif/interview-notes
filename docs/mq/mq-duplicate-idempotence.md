## 问题

面试官问：“消息队列为什么无法彻底避免重复消费？重复了怎么保证业务数据不出问题？”
考察对 at-least-once 语义的理解和幂等设计的落地能力，要求给出至少两种能直接上线的方案。

## 核心答案

1. 重复无法根除：MQ 的可靠性靠“超时重试 + 失败重投”实现，投递语义天然是 at-least-once。
   典型场景：生产者发送成功但 ack 网络丢失会重发；消费者处理完还没提交 offset 就宕机，重启后重消费。
2. 幂等方案一：消息携带全局唯一 ID（优先业务单号），消费前查去重表，已存在则直接 ACK 跳过。
   去重表的插入必须和业务操作放同一个本地事务，保证“已处理”和“已记录”原子生效。
3. 幂等方案二：Redis SETNX 以唯一 ID 为 key 做去重，设置成功说明首次消费，性能高、适合高并发。
   注意 Redis 与 DB 非原子，Redis 标记成功但业务失败时要删除 key 或回查业务状态。
4. 幂等方案三：数据库唯一索引兜底，如订单号唯一约束，重复插入直接报错，捕获异常后跳过即可。
   实现最简单、最可靠，通常与前两个方案组合使用。
5. 幂等方案四：状态机控制，如订单状态只允许 pending 到 paid，UPDATE 语句带前置状态条件。
   重复消息执行时影响行数为 0，天然被过滤，适合有状态流转的业务。
6. 失败重试与死信：消费失败进入重试队列，超过次数上限后转入死信队列并告警。
   由人工介入或补偿任务处理，注意补偿逻辑本身也要幂等。

## 深度解析

- 为什么不追求消息本身 exactly-once：端到端精确一次代价极高，且 Kafka 的 exactly-once 只覆盖 MQ 内部。
  跨系统的重复（MQ 到数据库）防不住，业务幂等是绕不开的最后一道防线。
- 去重表的坑：先标记后执行业务时，业务失败必须回滚标记，否则会出现“标记了却没处理”的死消息。
  所以去重记录必须与业务操作同事务，或者反过来“先业务后标记”。
- Redis 方案的坑：setnx 成功后业务失败若不删 key，这条消息永远不会被处理。
  处理方式：失败时删除 key 重新投递，或消费时再校验业务实际状态。
- 追问“幂等键怎么选”：优先业务天然单号（订单号、支付流水号），随机 UUID 在重试场景判不了重。
  因为每次重发生成的 UUID 都不同，只有稳定的业务键才能识别“同一条业务”。
- 追问“去重表性能”：高并发下去重表成为热点，可用 Redis 预判加数据库唯一索引兜底的两级结构。
