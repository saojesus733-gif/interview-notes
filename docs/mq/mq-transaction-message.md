## 问题

面试官问：“订单在本地事务里扣了库存，接着发 MQ 通知下游，消息发失败了怎么办？反过来先发消息、事务回滚了又怎么办？”
分布式一致性的经典难题，要求讲出 RocketMQ 事务消息或本地消息表至少一种完整方案。

## 核心答案

1. 问题本质：本地事务和“发消息”属于两个系统，无法用同一个事务包住，任何先后顺序都有中间态不一致。
   先落库后发消息：发送失败下游永远收不到通知；先发消息后落库：事务回滚但消息已经发出去了。
2. 方案一 RocketMQ 事务消息：先发半消息（此时对消费者不可见），再执行本地事务。
   事务成功则 commit，半消息转为正常消息被消费；失败则 rollback，删除半消息。
3. 回查机制：若 Broker 长时间等不到二次确认，定时回查生产者检查本地事务是否成功。
   根据检查结果 commit 或 rollback，解决“执行到一半宕机”导致的悬挂半消息。
4. 方案二 本地消息表：业务表与消息表在同一个本地事务中落库，消息初始状态为“待发送”。
   利用本地事务的原子性，保证“业务成功则消息记录必然存在”。
5. 本地消息表后续：定时任务扫描待发送记录投递 MQ，收到成功确认后标记完成；发送失败则重试。
   消息重发必然带来重复，下游消费必须幂等。
6. 方案对比：事务消息由中间件实现、业务侵入小，但绑定 RocketMQ 且有回查开销。
   本地消息表不依赖特定 MQ、任何团队都能落地，但要自己建表和扫描任务，增加数据库压力。两者都只保证最终一致。

## 深度解析

- 半消息不是数据库意义上的 prepare：它只是“暂不投递”的普通消息，回查机制才是补齐原子性的关键设计。
- 追问“消费失败了怎么办”：事务消息只保证消息一定发出，不保证下游一定处理成功。
  下游失败靠重试、死信和人工兜底，发送端与消费端合起来才是完整的最终一致。
- 本地消息表的常见误区：扫描任务没设重试上限和告警，坏消息无限重试刷爆日志。
  另外“标记完成”必须以 MQ 确认为准，本地发完就标完成会漏发。
- 追问与 TCC、Seata 的区别：要强一致用 TCC、Seata 这类分布式事务框架。
  能接受秒级最终一致时，事务消息或本地消息表是成本低得多的选择。
- 演进方案：用 Canal 订阅 binlog 投递 MQ 也是同思路——先保证本地事务成功，再可靠投递变更。
