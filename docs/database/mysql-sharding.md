## 问题

单表数据到了几千万甚至上亿、查询写入越来越慢，你会怎么做？
如果决定分库分表，拆分方式和分片键怎么选，拆完会引入哪些新问题？

## 核心答案

- **垂直拆分**：按业务把不同表拆到不同库、把大字段拆到扩展表；
  本质是业务解耦，改造难度低、风险小；
- **水平拆分**：同一张表按分片键路由分散到多个库表；
  真正解决单表数据量与 QPS 压力，但复杂度显著上升；
- **分片键选择**：优先选最高频的查询条件（订单用 user_id / order_id）；
  让绝大多数查询单分片命中，同时数据分布均匀、避免热点；
- **分片算法**：hash 分布均匀但扩容要迁移，range 利于范围查询但有冷热热点；
  扩容优先「翻倍扩容」只迁一半数据，或用一致性 hash、基因法缓解；
- **引入的新问题**：跨库 join 无法直接写、分布式事务、全局唯一 ID、跨片分页排序；
  这些是选型前就要想清楚的隐性成本；
- **对应方案**：join 改应用层组装或冗余字段；
  事务用最终一致（本地消息表 / Seata）；全局 ID 用号段模式或雪花算法；多维查询靠异构索引（ES、宽表）。

## 深度解析

- 原则：先垂直后水平、能不分就不分；
  先用索引优化、冷数据归档、读写分离顶住，分库分表是成本最高的最后手段。
- 分片数一次规划到位（常取 2 的幂，如 16 库 × 64 表），避免二次扩容全量迁移；
  用 ShardingSphere 等中间件统一路由，别把分片逻辑写死在业务代码里。
- 迁移方案：双写过渡——老库继续写、新库同步写；
  先全量 + 增量迁移并校验，再灰度切读，最后下线老库。
- 常见误区：为「数据均匀」选了一个查询里用不到的字段做分片键，导致几乎所有查询都扇出到全部节点再聚合，性能反而崩塌。
