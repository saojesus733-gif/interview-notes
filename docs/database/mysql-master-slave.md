## 问题

主从复制的完整链路是怎样的？异步、半同步、全同步各有什么取舍？
主从延迟是怎么产生的，线上有哪些应对手段？

## 核心答案

- **复制流程**：主库提交事务写 binlog，dump 线程推送给从库；
  从库 IO 线程接收写入 relay log（中继日志），SQL 线程再重放 relay log；
- **异步复制**：主库写完 binlog 即返回，不等从库确认；
  性能最好，但主库宕机可能丢尚未同步的事务；
- **半同步复制**：至少一个从库确认收到 binlog（写入 relay log）后主库才返回；
  兼顾安全与性能，等待超时自动降级回异步；
- **全同步复制**：等所有从库执行完才返回；
  一致性最强、性能最差，生产几乎不用；
- **延迟原因**：从库重放线程少（旧版本单线程）追不上主库并发写；
  大事务、大 DDL 重放慢，从库机器规格低或负载高；
- **应对手段**：开启并行复制（MTS）提升重放速度；
  读写分离时强一致读强制走主库，监控 Seconds_Behind_Master 并告警。

## 深度解析

- 经典坑「自己写自己读不到」：写完主库立刻读从库，数据还没同步过来；
  方案是关键业务强制走主库、会话内粘性读，或按 GTID 等待同步点位。
- GTID 复制：每个事务有全局唯一 ID，主从切换时自动定位复制位点；
  替代传统的 file + position 手工对位，故障切换更可靠。
- 半同步细节追问：等待点 AFTER_SYNC（写 binlog 后、提交前等 ack，更安全）与 AFTER_COMMIT 的区别；
  以及 ack 超时后静默降级为异步的监控告警。
- 一致性校验：定期用 pt-table-checksum 校验主从数据差异；
  差异小用 pt-table-sync 修复，差异大考虑重建从库。
