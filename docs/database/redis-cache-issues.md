## 问题

什么是缓存穿透、击穿、雪崩？三者分别怎么区分、怎么应对？
顺带谈谈你会怎么保证缓存和数据库的一致性。

## 核心答案

- **穿透**：查询根本不存在的数据，缓存永不命中，请求全部打到 DB；
  方案：缓存空值（短 TTL）、布隆过滤器前置拦截、接口层参数校验；
- **击穿**：某个热点 key 过期的瞬间，大量并发同时请求并打到 DB 重建；
  方案：互斥锁只放一个请求重建、热点 key 逻辑过期不删除；
- **雪崩**：大量 key 同时过期或 Redis 整体宕机，DB 被瞬时流量打垮；
  方案：过期时间加随机值打散、多级缓存（本地 + Redis）、限流降级兜底、集群高可用；
- **一句话区分**：穿透是「查不存在的数据」，击穿是「单个热点 key 失效」；
  雪崩是「大面积 key 同时失效或缓存整体不可用」，三者影响范围依次扩大；
- **一致性基础策略**：Cache Aside——读时先查缓存、未命中回源写缓存；
  更新时先更新数据库，再删除缓存，并靠过期时间兜底；
- **增强手段**：延迟双删（更库删缓存后，隔几百毫秒再删一次）缩小不一致窗口；
  要求更高时用 binlog 订阅（Canal）异步删除缓存。

## 深度解析

- 为什么「先更库再删缓存」：删除后下一次读自然回源，逻辑简单、不一致窗口极小；
  「先删缓存」在并发读写交错时更容易让旧值长时间留在缓存里；
- 布隆过滤器说「不存在」一定准确，说「存在」可能误判；
  误判率取决于位数组大小与哈希个数，标准布隆不支持删除，需要删除可换布谷鸟过滤器；
- 互斥重建 vs 逻辑过期：前者强一致但请求阻塞排队，后者可用性高但短期返回旧数据；
  按业务对一致性与可用性的容忍度选择；
- 常见误区：三者混为一谈——穿透是「无中生有」，击穿与雪崩是「失效问题」，区别只是失效范围；
- 追问点：缓存与 DB 的强一致基本做不到；
  答题先声明业务可容忍的一致性级别，再谈方案取舍。
