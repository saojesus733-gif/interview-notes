## 问题

设计一个电话语音客服 Agent。语音场景对延迟和"打断"极其敏感，链路怎么设计？延迟预算怎么分配？

## 核心答案

**链路**：流式 ASR（语音转文字）→ LLM → 流式 TTS（文字转语音），全链路流式衔接。

**延迟预算（体感分界）**：

- 端到端响应 ≤ 1 秒优秀，1.5~2 秒可接受，超 3 秒对话开始"卡顿"；
- 拆分预算：VAD 端点检测 ~200ms + ASR 首字 ~200ms + LLM 首 token ~500ms + TTS 首包 ~300ms，其余留给网络与调度——**每一环都要流式**，任何一环攒完整段再输出就会爆预算。

**关键设计**：

1. **流式贯通**：ASR 边说边转字；LLM 边生成边出 token；TTS 按句/分片合成播放——不等整句；
2. **提前响应**：VAD 检测用户说完即触发（不等 ASR 完全静止）；LLM 用低 TTFT 模型/就近部署；高频话术（问候/确认）走模板直达 TTS，不进 LLM；
3. **打断（Barge-in）**：用户插话 → 立即停 TTS 播报 → 丢弃正在生成的 LLM 输出 → 把"用户已说的话"重新送入 ASR/LLM 理解；需要回声消除（AEC）防止 Agent 自己的声音被误识别为用户语音；
4. **话术适配**：短句优先、避免长列表朗读；重要数字（金额/工号）放句尾并支持复述。

## 深度解析

- 语音 Agent 的本质是把"延迟工程"叠加在 LLM 应用上：文本场景 2 秒可接受，语音场景 2 秒就是事故——架构上每个组件都要选"流式接口"版本；
- 加分点：打断的状态机（播放中→被打断→重置上下文）要明确到"哪些已生成的 token 作废、哪些已确认的用户语音保留"；
- 分级响应：极简意图（"好的""稍等"）可以用小模型甚至规则直接回复，把大模型留给复杂问题。
