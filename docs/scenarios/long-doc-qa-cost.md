## 问题

产品要求支持对几百页的 PDF 文档精准问答。有同事提议"直接把全文塞进长上下文模型"，你评估一下这个方案，并给出你的设计。

## 核心答案

**评估"全文塞窗口"**：技术上可行但三个问题——

1. **成本**：几百页 ≈ 几十万 token，每个问题都要全量付费一次（多轮对话重复付）；
2. **效果**：超长上下文存在"中间信息丢失"，关键页在中间时回答质量下降；延迟数十秒起步；
3. **并发**：单请求几十万 token 会长时间占用推理资源，高并发基本不可行。

**我的设计：RAG 为主、长上下文兜底**：

```text
离线：PDF 解析（版面/表格还原）→ 按章节结构切分 → Embedding 入库（保留页码/章节元数据）
在线：用户问题 →（可选）改写 → 混合检索 Top-K → Rerank 取 Top-5~10
      → 引用片段 + 问题拼 Prompt → 生成（带页码引用）
兜底：检索置信度整体偏低（如全文总结类问题）→ 才走长上下文/分段 Map-Reduce 摘要
```

**关键细节**：

- PDF 解析质量决定上限：双栏排版、表格、图表要专门处理，必要时版面分析模型；
- 引用要能定位到页码，用户可核验（也是压幻觉手段）；
- 对"通读全文型"问题（总结全书）用 Map-Reduce：分段摘要 → 再汇总，避免单窗口硬塞。

## 深度解析

- 成本对比：RAG 单次问答只带几千 token 上下文，比全文方案低两个数量级；缓存（同文档同问题）与多轮只增差距；
- 加分点：给出分流规则——"点状问题走检索，全局问题走摘要链，两者都低置信再走长上下文"，并强调用评估集对比三种路径的准确率与成本再定阈值；
- 该题考察"不为炫技上长上下文"的工程判断。
