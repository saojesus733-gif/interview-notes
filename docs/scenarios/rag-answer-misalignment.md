## 问题

你的知识库问答系统上线后，用户反馈"经常答非所问"。假设你只能拿到线上日志，给出你的排查思路和优化顺序。

## 核心答案

**第一步：先分层定位（检索问题还是生成问题）**——抽 30~50 条差评 case，对每条回答三个问题：

1. 检回的内容里有没有答案？（没有 → 检索问题）
2. 检回的内容相关吗？排序靠前吗？（不相关/排序差 → 检索排序问题）
3. 资料里有答案，模型答对了吗？（有料但答错 → 生成问题）

**第二步：按归因分类优化**：

- **该检没检到（Context Recall 低）**：查切分是否把答案切碎、query 与文档措辞差异大 → 加混合检索、query 改写、调大 chunk；
- **检到但排序差（Context Precision 低）**：加 Rerank、调 RRF 权重；
- **检到了答错（生成问题）**：Prompt 约束不足、资料位置太远、模型能力不够 → 强化"仅依据资料回答"、相关资料贴近问题放置、换更强模型；
- **用户问题本身超纲**：知识库根本没覆盖 → 这不是 bug，设计"未覆盖就拒答/引导人工"的路径。

**第三步：建立回归闭环**——把差评 case 标注进评估集，每次优化跑回归，防止按下葫芦浮起瓢。

## 深度解析

- 排查顺序背后是成本逻辑：检索侧优化（免重训、见效快）永远先于生成侧；「用户超纲」的 case 要单独统计，它影响的是产品预期管理而非技术优化。
- 加分点：给出量化口径——差评 case 按四类归因出百分比（如检不到 40% / 排序差 30% / 答错 20% / 超纲 10%），资源投向最大头。
- 面试官想听的是"工程化排查框架"而非单点技巧，先框架后细节。
