## 问题

业务方想要"用自然语言查数据"（ChatBI）：用户问"上个月华东区销售额 Top10 的商品"，系统自动查库出报表。直接让 LLM 写 SQL 行吗？怎么设计？

## 核心答案

**直接裸奔的三个问题**：不知道你的表结构（schema）、不知道业务口径（"销售额"含不含税？）、生成的 SQL 不可控（可能全表扫描/越权）。

**参考设计**：

1. **Schema 注入**：把相关表结构、字段含义、枚举值、示例行放进 Prompt（大库先做"表检索"只注入相关表）；
2. **口径层（Semantic Layer）**：业务指标（GMV、活跃用户）定义为**受管的指标对象**（口径+SQL 模板），LLM 只负责选指标+填参数，不自由发挥聚合逻辑——口径不一致是 ChatBI 的头号失败原因；
3. **Few-shot**：给 3~5 个"问题→SQL"示例对，覆盖典型与复杂模式；
4. **生成约束**：只允许 SELECT、方言固定（MySQL/ClickHouse 语法）、LIMIT 强制、禁 DDL/DML；
5. **执行前校验**：SQL 解析器校验语法与涉及表、权限服务校验用户行级权限、超时与行数上限；
6. **结果回填**：执行结果（截断后）返回 LLM 生成自然语言摘要 + 表格，附生成的 SQL 供用户核对；
7. **歧义澄清**：指标/时间范围有歧义时先反问，不猜。

**评估**：用"问题 → 标准答案 SQL/结果集"建测试集，按执行结果比对算准确率，分难度分层看。

## 深度解析

- 加分点：权限是底线——数据库账号只读 + 行级权限过滤在 SQL 层强制注入（如追加租户条件），模型无权决定权限；
- 复杂问题的策略：拆解成多步（先查子查询再组合），Agentic 化；但简单问题走"指标模板直译"更快更稳；
- 该场景与数据工程强耦合：数据质量差（脏数据/口径混乱）时，ChatBI 会忠实放大混乱——先治理数据再上 LLM。
