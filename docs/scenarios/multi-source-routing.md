## 问题

企业知识散落在四处：FAQ 库、文档库、业务数据库（结构化）、实时接口（订单/库存状态）。问答系统怎么决定去哪查、怎么融合结果？

## 核心答案

**分层路由设计**：

1. **意图分类**：先把问题分型——事实咨询（FAQ/文档）、统计型（数据库）、状态型（实时接口）、闲聊（不查）；
2. **静态规则优先**：能用便宜规则命中的先命中——FAQ 精确/高相似匹配直接返回（毫秒级零成本）；
3. **动态路由**：分类器或 Agent 决定查哪路（可多路并行）：
   - 文档类 → 向量检索 + Rerank；
   - 统计类 → Text2SQL/指标模板；
   - 状态类 → 调实时 API；
4. **冲突融合**：多路都命中时按**优先级**取用——实时接口 > 文档库 > FAQ（时效性排序），并在答案中标注信息来源与时间；
5. **兜底**：全部未命中 → 拒答 + 转人工，把人工答案回流进对应知识源。

**运营要点**：每条路独立监控（命中率、使用率、延迟）——路由错误是"复合错误"的第一环，必须单列指标。

## 深度解析

- 路由器的演进路径：硬编码规则 → 小模型分类器 → LLM/Agent 动态决策，按收益逐级升级，不要第一天就上 Agent 路由；
- 冲突处理是隐藏考点：FAQ 说"支持退款"、新政策文档说"该品类不支持"——没有优先级规则时模型随机选；答案：按数据源建立**时效与权威等级**，检索时过滤过期源；
- 与 Agentic RAG 呼应：这里的路由就是 Agent"决定查什么"的具体化，规模小用分类器，规模大用 Agent + 工具描述。
