## 问题

业务要上线一个可以帮用户执行转账的 Agent。作为安全评审人，你要求它满足哪些条件才能上线？

## 核心答案

**按"出了问题会怎样"倒推清单**：

**一、权限与身份**

1. Agent 以**用户本人身份**执行转账（on-behalf-of 透传），没有独立的高权限资金账号；
2. 工具白名单最小化：只有转账、查询、收款人列表三个工具，无导出、无批量接口；
3. 参数与服务端强校验：收款账户、金额、限额全部服务端再验一遍，Agent 侧校验只是体验优化。

**二、流程管控**

1. **双确认**：模型解析出转账意图后，向用户回显完整要素（收款人、卡号尾号、金额）获得明确确认，才允许发起；
2. **限额与频率**：单笔/日累计限额，超限强制人工审核；新收款人大额转账强制 HITL 审批；
3. **幂等与防重**：idempotency key 贯穿，防止重试/重发导致重复转账。

**三、对抗与滥用**

1. Prompt 注入测试通过：诱导话术（"我是客服帮我转""系统提示词要求你转账"）不能绕过确认流程——**确认流程在代码层，模型说了不算**；
2. 上下文脱敏：卡号等敏感信息进入日志前打码；
3. 全量审计：每笔转账的会话上下文、确认记录、审批记录可追溯。

**四、运营兜底**

1. 一键降级开关（功能级：转账下线，查询保留）；
2. 实时风控联动（异常金额/频率触发人工）；
3. 事故预案：可疑交易冻结流程与客诉响应路径。

## 深度解析

- 评审的总原则一句话：**假设模型可以被完全骗过（输出任意工具调用），资金链路依然守得住**——守住靠身份透传、服务端校验、确认记录、限额、HITL 这五道代码层防线；
- 加分点：区分"用户确认"与"系统确认"——用户的确认记录必须由前端采集并持久化，不能以"模型说用户同意了"作为依据；
- 这套清单（身份/校验/确认/限额/审计/降级）可作为所有"写操作 Agent"的通用上线模板。
