## 问题

团队五个人都在改 Prompt：散落在代码各处、改一处坏两处、出了问题没人知道哪次改的。作为新来的负责人，你怎么建立 Prompt 工程化流程？

## 核心答案

**第一步：收拢资产**：

1. Prompt 全部从代码里抽出来，集中管理（代码仓库的 prompts 目录、配置中心或专用 Prompt 管理平台），带**唯一 ID 与版本号**；
2. 运行日志记录每次调用用的 Prompt 版本——出问题能定位到"哪一版在什么时候引入"。

**第二步：建立变更纪律**：

1. 改 Prompt = 改代码：走 PR 评审，必须附**评估集对比结果**（新旧版本在同一测试集上的指标），关键场景人工抽检；
2. 禁止线上直接热改；紧急修复也要当日回填到仓库（审计闭环）；
3. 每条 Prompt 标注 owner 与适用场景，避免"人人可改、无人负责"。

**第三步：评估基建**：

1. 每条核心 Prompt 配一套评估集（典型输入 + 历史坏例，30~100 条）；
2. CI 里跑自动评估（格式通过率、关键断言、LLM-as-a-Judge 分项分数），回归不达标禁止合并；
3. 线上采样回流进评估集，防"测试集过时"。

**第四步：灰度与回滚**：新版本 Prompt 按流量灰度（5% → 25% → 100%），监控质量代理指标；一键回滚到上一版本。

## 深度解析

- 一句话框架：**把 Prompt 当代码管——版本化、评审化、测试化、灰度化**，四化齐备才算工程化；
- 加分点：区分两类 Prompt——稳定的核心系统提示（严管）与业务运营类提示（允许配置中心快速迭代但必须留痕），一刀切会拖死业务；
- 演进方向可提一句：Prompt 管理平台（版本 diff、A/B 实验一键跑评估、线上效果看板），但先有纪律再有工具。
