## 问题

Agent 依赖的一个第三方数据接口平均响应 8 秒、超时率 5%，导致整个任务链路又慢又不稳。怎么设计？

## 核心答案

**分层处理**：

1. **调用层加固**：
   - 超时分级（连接/读取超时都收紧到业务可接受值），重试只对幂等查询、配退避与上限；
   - 熔断：连续失败即熔断一段时间，直接走降级路径，不再等它超时；
2. **结果缓存**：该接口数据变化不频繁 → 加 TTL 缓存（Redis），命中率直接决定体验；缓存键含关键参数，注意数据新鲜度要求；
3. **异步化**：若业务允许，把同步等待改成"提交任务 + 轮询/回调"——Agent 先答复"已受理"，结果到达后继续（任务挂起恢复机制）；
4. **Agent 行为适配**：
   - 把该工具标注为"慢工具"，System Prompt 约束"非必要不调用、调用后不要重复请求"；
   - 模型多次等待同一接口失败时，注入"该数据源暂不可用，基于已有信息作答或告知用户稍后查询"的引导；
5. **降级与预期管理**：熔断/超时的降级路径优先级：缓存旧数据（标注数据时间）> 类似数据源 > 告知用户"该信息暂不可查"。

## 深度解析

- 原则：**外部依赖的不可靠不可以通过重试堆给模型**——模型在长等待里只会放大成本与震荡，可靠性必须在代码层解决；
- 加分点：量化思维——先算"该接口贡献了多少 P95 延迟与失败率"，优先级才有依据；修完后用轨迹数据验证（平均轮数下降、超时率下降）；
- 这题考的是把传统微服务稳定性手段（超时/重试/熔断/缓存/降级）与 Agent 执行循环结合的意识。
