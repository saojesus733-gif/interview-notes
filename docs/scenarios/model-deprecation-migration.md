## 问题

供应商通知：你重度依赖的模型半年后下线（或价格翻倍）。你的应用有几十处 Prompt 深度适配了它的行为。怎么迁移？

## 核心答案

**第一步：盘点影响面（1 周）**

- 梳理调用清单：哪些应用/哪些链路用了该模型、各自的效果依赖程度；
- 区分"普通调用"（可平替）与"深度依赖"（依赖特定行为：格式习惯、工具调用风格、长上下文能力）。

**第二步：候选模型离线评估（2~4 周）**

- 选 2~3 个候选模型，跑同一评估集（这正是平时就该有的资产）；
- 对比正确率、格式通过率、延迟、成本；差距大的场景定位到 Prompt 层修补。

**第三步：适配与验证（4~8 周）**

- Prompt 微调：输出格式约定、few-shot 示例换成新模型生成口径；
- 行为差异修补：工具调用参数风格、拒答话术、温度/解码参数重调；
- **影子流量**：新模型对真实请求只算不回，与旧模型输出离线 diff。

**第四步：灰度切换（4 周）**

- 按流量 5% → 25% → 100% 灰度，监控质量代理指标与成本；
- 全量后旧模型保留只读回滚能力至下线。

## 深度解析

- 这题的高级答案是"让迁移从项目变为例行动作"：平时就做三件事——网关统一协议（换模型改配置）、评估集常态回归（每月跑一遍候选模型基线）、避免硬绑定私有特性；
- 半年周期看似宽裕：真正耗时的不是切换而是"行为差异的发现"，影子 diff 能把人工排查压缩一个量级；
- 顺带的收益：多模型基线数据会成为成本优化（模型分级路由）的输入。
