## 问题

LLM 应用上线后如何监控？模型没改、代码没动，回答质量却变差了，怎么发现和排查？

## 核心答案

**监控体系（四类信号）**：

1. **系统指标**：延迟（TTFT/P99）、错误率、QPS、SSE 中断率——传统可观测；
2. **成本指标**：token 消耗（分输入/输出）、缓存命中率、费用——突变常是问题前兆（如上下文意外膨胀）；
3. **质量代理指标**：拒答率、格式解析失败率、工具调用失败率、用户负反馈率、答案编辑率、转人工率——线上最灵敏的质量信号；
4. **抽样深度评估**：线上流量按比例抽样，用固定评估集/LLM-as-a-Judge 自动打分，画趋势线。

**质量退化排查框架（题眼：模型没改代码没改）**：

```text
先确认「真的退化」：评估集回归 + 抽样对比，排除业务流量变化（新场景用户变多）
  ↓ 逐层归因
1. 模型侧：厂商是否静默换版本/更新（API 模型行为漂移）→ 固定模型版本号 + 对照测试
2. 输入侧：用户 query 分布变化？新业务入口引入新类型流量？
3. 上下文侧：RAG 检索质量是否下降？（知识库内容被改动/索引过期/Embedding 服务变更）
4. 工具侧：外部 API 返回结构变化导致信息缺失？
5. 基础设施：网关重试、超时参数、缓存放大问题？
```

**防线**：模型版本锁定与灰度、变更关联分析（把每次 Prompt/模型/知识库变更打标进监控时间线）、退化告警（质量代理指标突破基线）。

## 深度解析

- LLM 应用特有风险是「外部依赖的静默变化」：闭源模型行为漂移、知识库被运营改动、Embedding 服务升级——都需要版本化与对照基线才能发现；
- 「质量退化」要区分绝对退化与分布漂移：老用户问题答得差是退化，新类型问题答得差是覆盖不足，对策不同；
- 事后可回放：全量请求响应留痕（脱敏），退化发生时可重放评估，定位到具体变更点。
