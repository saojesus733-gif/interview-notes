## 问题

Prompt/模型/检索策略的变更都要上线，LLM 应用怎么做灰度与 A/B 实验？

## 核心答案

**为什么 LLM 应用必须灰度**：变更影响的是"回答质量"这种难以事前完全验证的属性，且线上流量分布与评估集总有差异——小流量验证是最后一道防线。

**标准流程**：

1. **变更打标**：每个变更（Prompt 版本/模型版本/检索参数）有唯一标识，日志按变更分组——这是归因的基础；
2. **影子模式（可选先行）**：新版本对真实流量只跑不回（结果记日志不返回用户），零风险拿到线上分布的离线对比；
3. **A/B 分流**：按用户/会话维度哈希分桶（保证同一用户体验一致），对照组旧版本、实验组新版本；
4. **指标对比**：业务指标（完成率/采纳率/转人工率）+ 质量代理指标（负反馈/重试率）+ 成本延迟；样本量按期望效应预估，避免"看几天波动就下结论"；
5. **放量与回滚**：5% → 25% → 100% 阶梯放量，任一关键指标显著恶化即一键回滚（版本切换在配置层，秒级生效）。

**注意事项**：

- 会话级一致性：同一会话固定版本，避免前后回答风格/行为跳变；
- 长尾敏感：均值差不多时，看坏 case 率（P95、负反馈率）再决策；
- 每次实验结论沉淀进评估集，让离线评估越来越能代表线上。

## 深度解析

- A/B 与评估集是互补关系：评估集管"快速回归与防倒退"，A/B 管"真实流量下的最终裁决"——只做后者迭代太慢，只做前者会与线上漂移；
- 加分点：LLM 应用的"变更面"比传统应用大（Prompt/模型/检索参数/工具描述都能变），统一变更管理与打标体系是 A/B 能做起来的前提；
- 灰度粒度可按"功能域"而非全局：新 Prompt 只影响一个意图域时，只在那个域分流，实验更干净。
