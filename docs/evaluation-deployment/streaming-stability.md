## 问题

LLM 应用的流式输出链路上有哪些稳定性风险？工程上怎么保障？

## 核心答案

**流式链路的主要风险与对策**：

1. **超时**：模型长响应/卡死 → 分层超时（连接超时、首 token 超时、总时长超时）+ 到时优雅截断（输出已生成部分 + 收尾提示）；
2. **中断与重试**：流式响应**不可简单重试**（用户已看到一半）——策略：无输出时重试安全；已输出后中断则续写（带已生成内容上下文）或整段重来需用户确认；
3. **断线重连**：SSE 客户端自动重连 + 事件 ID 续传；服务端保留最近输出缓冲，支持「接着看」；
4. **降级路径**：主模型不可用 → 切备用模型；流式不可用 → 降级为整段返回；全挂 → 缓存答案/兜底话术；
5. **背压与并发控制**：网关限制单用户并发流数，防重复提交打爆配额；客户端防抖；
6. **数据完整性**：流式断了但业务要记账——生成结果由服务端持久化（异步落库），不依赖客户端收全。

**监控指标**：TTFT（首 token 延迟）、流中断率、重连率、降级触发率、生成完成率。

## 深度解析

- 流式的「事务性」难题：LLM 输出没有天然的 commit 点，工程上把「完整生成内容落库」作为事实源，流只是展示通道——两端解耦后中断就只是展示问题；
- 幂等键贯穿：用户重试/重连都带同一请求 ID，服务端识别为同一任务，避免重复计费与重复生成；
- 混沌演练：主动注入模型超时、半途断流、网关断连，验证降级与续传真的生效。
