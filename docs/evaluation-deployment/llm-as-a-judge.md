## 问题

什么是 LLM-as-a-Judge？用它做自动评估有哪些偏差？怎么克服？

## 核心答案

**定义**：用（更强的）LLM 按照评分标准（rubric）对另一个模型的输出进行打分或排序，替代部分人工评估——把「好不好」变成可规模化、可回归的自动评估。

**标准做法**：

1. 定义结构化 rubric：评估维度（忠实度/相关性/完整性/语气）+ 每档分数的判据 + 输出格式（分数 + 理由）；
2. 提供参照（标准答案 / 检索资料 / few-shot 评分示例）；
3. 多样本批量评估，汇总分布而非单点。

**已知偏差**：

1. **位置偏差**： pairwise 比较时偏向先出现的答案 → 对比时交换顺序各评一次取一致结果；
2. **长度偏好**：偏爱更长、更面面俱到的回答 → rubric 里显式惩罚冗余，或限制长度权重；
3. **自我偏好**：模型偏爱自己（同家族）的输出 → Judge 与被评对象用不同家族模型；
4. **评分漂移**：不同批次打分尺度不一致 → 每批插入锚定样本（已知质量的金标准）校准。

**有效性验证**：抽一批样本做人工标注，算 Judge 与人工的一致率——**对齐了人工的 Judge 才有资格上岗**。

## 深度解析

- Judge 的价值在「相对比较与回归」，不适合做绝对事实裁决：事实类判断应交给检索比对/工具核验，而不是另一个模型的「感觉」；
- rubric 工程是核心投入：维度越具体、判据越行为化（「答案中的每个数字都能在资料中找到」），Judge 越稳；
- 成本结构：Judge 调用也有 token 成本，评估集大时用小模型初筛 + 强模型复核分层跑。
