# 智居 Agent（房源推荐与预约）— 追问准备册

> 简历一句话：LangGraph 编排的租房 Agent，主图意图路由 + 推荐/预约/闲聊子图，interrupt 中断恢复补全需求，LangChain SQL 工具链生成校验查询 MySQL，LangGraph Store 存偏好与预约记录，PG 存线程状态。
> 仓库：github.com/saojesus733-gif/house-agent

## 电梯稿（30 秒，背熟）

> 租房这个场景对话轮次多、要跨会话，普通聊天机器人做不到"记住你、断掉了还能续"。我用 LangGraph 做了一个多子图 Agent：主图做意图路由，推荐、预约、闲聊各是一个子图；需求没说全会用 interrupt 暂停下来收集参数，状态全部 checkpoint 到 PostgreSQL，用户三天后回来还能接着聊；房源查询用 LLM 生成 SQL，程序侧校验后执行。整条链路从需求补全到预约看房是业务闭环。

## 高概率追问链（含参考答案）

### 一、架构选型（必问）

**1. 为什么拆推荐子图和预约子图？单图不行吗？ReAct 和状态机怎么区分？** ⭐3

参考答案：拆分是因为两个子任务的状态结构和流程完全不同——推荐子图围绕"查询条件→检索→排序"，预约子图围绕"信息收集→校验→出工单"，混在一个图里 state 会膨胀、条件边爆炸。关于 ReAct 和状态机：租房场景的路径是**可枚举的**（就是那几个步骤），所以用图编排确定性流程，LLM 只在节点内部做总结和生成，可控且省 token；ReAct 适合路径不可预知的开放任务。如果面试官说"这其实就是工作流"——**承认并深化**：对，推荐子图本质是工作流，我刻意把确定性放在代码里，只把语言理解交给模型，这是设计而非局限。

### 二、Interrupt 中断恢复（王牌，必须讲透）

**2. interrupt 的原理是什么？状态存在哪？断线重连怎么续上？** ⭐3

参考答案（三段式）：
- **为什么需要**：需求补全要用户输入。没有持久化，用户填到一半关页面，会话就死了；有了 checkpoint，对话是可以"暂停再续"的。
- **机制**：LangGraph 每个节点执行完都会把整条线程的 state checkpoint 写入 PostgreSQL（PostgresSaver）。执行到 `interrupt()` 时，图在这个节点暂停，把要收集的信息（表单结构）抛给前端，线程停在断点；用户提交后用 `Command(resume=表单值)` 恢复执行，暂停节点直接拿到值继续跑。恢复不是"重放历史"，是**从 checkpoint 里加载状态后从断点继续**。
- **断线/三天后回来**：前端凭 thread_id 拉线程当前状态，发现处于 interrupt 中断点就重新渲染那张表单；checkpoint 在库里，随时可续。

追问"和自定义 state 字段管理多轮会话比，为什么两个都用"：state 字段管的是**业务内**的多轮（比如用户改预算），interrupt 管的是**跨等待**的中断（要用户人在场输入）——粒度不同，配合使用。

### 三、SQL 生成与校验（简历写了"生成并校验"，必被追问）

**3. 生成的 SQL 怎么校验？查询错了怎么兜底？** ⭐3

参考答案（分层讲）：
1. **生成约束**：prompt 里只给白名单表结构和字段说明，要求只生成 SELECT；
2. **程序校验**：执行前检查——只读账号执行（数据库层面就没有写权限）、解析 SQL 确认无 DML/DDL、强制 LIMIT；
3. **失败重试**：执行报错时把错误信息回传给 LLM 修正，最多重试 2 次；
4. **兜底**：仍失败就告诉用户"换个条件试试"，不让错误裸奔给用户。
- 追问"防注入"：只读账号 + 白名单表列 + 禁止字符串拼接用户输入。
- 追问"Text2SQL 准确率"：用【填你的数字，如 30 条标注查询自测 hit 率 ~90%】的自测集，说清评测方法比数字本身重要。

### 四、意图识别与记忆

**4. 意图路由怎么知道分对了？相似问法不同意图怎么办？** ⭐2

参考答案：路由是 prompt + few-shot 的 LLM 分类；准确率用自测问句集量化【填你的数字】。相似问法不同意图——单靠语义相似度确实分不开，所以要结合**槽位状态**：比如"我想看看别的"在有推荐结果的上下文里是翻页意图，在开场是推荐意图；分不清时用 interrupt 式澄清反问确认，而不是硬猜。

**5. Store 里的偏好，用户回来后按旧的推还是重新问？** ⭐3

参考答案（这是迅雷面试官说他们没解好的开放题，给框架不装懂）：我的做法是偏好作为**候选**注入 prompt，同时**显式确认**——"上次你说预算 3000，还按这个来吗？"核心思路：让确认成本低于猜错成本；偏好带更新时间，过期的不自动用。诚实补充：完全自动判断"该用旧方案还是新方案"没有银弹，确认交互是工程上最稳的解。

### 五、杂项快答

**6. PG 存 LangGraph 状态、MySQL 存业务数据，为什么分开？** — saver 生态 PG 最成熟（官方实现），框架状态和业务数据生命周期不同，分开各自演进互不拖累。

**7. 预约收集手机号/身份证，怎么处理敏感信息？重复下单怎么防？** — 敏感字段只在生成工单时使用、日志不落明文；工单生成后清空会话预约状态，且校验目标房源必须来自当前会话的推荐列表，防重复和防伪造。

**8. 房源表加了新字段（如地铁线），链路哪里要改？** — 只改 prompt 里的 schema 描述和白名单，编排代码零改动——schema 是元数据驱动的。（对标字节场景题"表结构变了怎么处理"）

## 危险区

- interrupt 被追"重启服务后线程还在吗"——在，checkpoint 落库了，和代码部署无关
- 说不出 Text2SQL 的评测方法——准备一个 30 条左右的自测集口径
- 三个数字必备：房源量级【填】、意图路由准确率【填】、预约流程完成率【填】
