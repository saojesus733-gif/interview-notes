# 实习：企业办公 AI 助手 + 数据 Pipeline — 追问准备册

> 简历一句话（公司匿名化）：在企业协作 SaaS 公司实习，参与企业办公 AI 助手（审批规则/考勤制度 RAG 问答 + 受控 Agent Tool），以及 Teambition 数据接入 Pipeline（1000+ 任务记录，增量同步 + 可靠性机制）。

## 电梯稿（30 秒，背熟）

> 实习在一家企业协作 SaaS 公司做 AI 应用开发，两块工作：一是企业办公 AI 助手，围绕审批规则和考勤制度做 RAG 问答，带来源引用，并给任务查询设计了受控的 Agent Tool 调用边界；二是这个助手的数据底座——把 Teambition 的任务数据通过 OpenAPI 和 Webhook 接进来，做了增量同步加可靠性机制：SQLite 持久化队列、事件去重、失败重试、死信处理、定时全量校准，保证 Agent 查到的数据是可信的。

## 高概率追问链（含参考答案）

### 一、受控 Agent Tool（差异化亮点）

**1. "受控"的边界具体怎么设计？为什么不让 Agent 自由调用？** ⭐3

参考答案：制度问答场景对错误零容忍，Agent 自由决策工具调用一旦幻觉就会查错数据误导用户。所以边界是三层：**工具层**只暴露任务查询这一个只读 Tool，没有写操作；**参数层**用 schema 约束（部门/时间范围/任务状态是枚举值，LLM 只能填槽不能自由发挥）；**执行层**参数校验失败直接拒绝并返回引导话术，不做模糊执行。一句话总结：LLM 负责"理解用户要什么"，取数的路径是写死的——把幻觉挡在数据之前。参考 [Agent 的安全执行与沙盒边界](/evaluation-deployment/agent-security-execution)。

**2. RAG 回答制度问题，怎么让用户敢信？来源引用怎么实现？** ⭐2

参考答案：检索时每个召回片段带文档 ID 和段落定位；生成时 prompt 要求"仅基于给定材料回答，并标注引用编号"；前端把编号渲染成可点击的原文出处。无法从材料回答的问题，直接说"制度文档里没有相关条款"，禁止模型自由发挥。这是对抗幻觉最硬的手段：**答案和证据绑定**。

### 二、数据 Pipeline 与可靠性（"1000+"必被质疑）

**3. 增量同步和定时全量校准，为什么两个都要？只用一个行不行？** ⭐3

参考答案：不行，两者解决的是不同问题。增量（Webhook 驱动）保实时，但它天然有**丢事件**的可能——推送时服务重启、网络抖动、对端限流丢弃，丢一次数据就永久不一致。定时全量校准是**对账**：周期性拉一遍最新状态覆盖本地，把增量阶段的任何丢失和乱序修正回来。增量管"快"，全量管"对"，生产级同步的标准双保险。

**4. 事件去重怎么做的？幂等怎么保证？** ⭐3

参考答案：Webhook 会重复推送（对端 at-least-once 语义）。去重键用**事件 ID**，落库加唯一约束——重复事件插入冲突直接跳过；处理侧用状态表记录"已处理"标记，处理逻辑本身用批量 upsert（按任务 ID 主键覆盖写），天然幂等：同一条事件处理三次和一次的结果一样。

**5. 失败重试和死信处理具体怎么做？** ⭐2

参考答案：处理失败的事件带重试计数退避重试（立即→延迟→再延迟），超过阈值标记为**死信**不再阻塞队列，同时日志告警；死信不丢，修复诱因（比如字段映射规则变了）后可以人工重放。JSONL 日志按事件 ID 记全链路，排查时一条事件从入队到落库全程可追溯——这就是简历那句"提升故障排查效率"的具体含义，要能讲一个真实案例【填：你排查过的某个具体问题】。

**6. 为什么用 SQLite 做持久化队列，不用 Redis 队列 / MQ？** ⭐2

参考答案（权衡 + 演进，和 AIWear 的 pgvector 同一答法框架）：当前数据量小（千条级），SQLite 零部署依赖、文件即数据库，而且**入队和处理可以在同一事务里保证原子性**——服务崩溃队列也不丢，这对可靠性需求是本质优势。边界：写入并发高或数据到百万级，SQLite 单写锁就是瓶颈，那时换 Redis Stream 或 MQ。我不否认它是轻量方案，但它是**当前规模下正确性最高、复杂度最低**的方案。

**7. Teambition OpenAPI 限流吗？Webhook 丢了怎么办？** ⭐2

参考答案：有频率限制，客户端做了【按你实际实现填：限速/退避重试】；Webhook 丢失靠定时全量校准兜底（回到第 3 题的逻辑）——所以单个通道不可靠没关系，机制上冗余了。

### 三、诚实面对"数据量小"

**8. "1000+ 条"是不是量太小了？你真正学到的是什么？** ⭐3

参考答案（转化，不防御）：数据量由客户业务规模决定，不由我决定；我负责的是**机制的正确性**——去重、幂等、重试、死信、对账这套机制在 1000 条和 100 万条时逻辑是同一套。如果数据 ×1000，我会改三处：队列换 Redis Stream、批量窗口加大、同步任务并行分片——说得出"什么会先坏、坏了怎么换"，比数据量本身更能说明工程能力。

## 危险区

- "参与"被拷：字节原题"你承担什么角色、团队几人"——如实切分你独立做的部分（受控 Tool 的边界设计、去重与死信机制）和跟做部分，别含糊
- 讲不出一个具体排障故事：准备一个 JSONL 日志定位问题的真实案例【填：时间线 + 现象 → 定位 → 修复】
- 和 AIWear 的 RAG 讲混：一个考勤制度文档（结构化问答 + 来源引用），一个穿搭知识库（多模态场景）——场景和方案差异要能一句话说清
