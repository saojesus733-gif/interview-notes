## 问题

下单要同时扣库存、扣余额、发消息，跨了三个服务，数据不一致怎么办？
说说你知道的分布式事务方案，以及实际项目里你会怎么选型。

## 核心答案

- 2PC/XA：准备 + 提交两个阶段由协调者统一决策，强一致；但同步阻塞、协调者单点，
  性能差，适合数据库层短事务。

- TCC：Try 预留资源、Confirm 确认、Cancel 释放；性能好于 2PC 但业务侵入大，每个操作要写三个接口，还要处理空回滚、悬挂。

- 本地消息表：业务数据和消息在同一个本地事务里落库，再由后台任务把消息投递给下游，靠重试保证最终一致。

- 事务消息：RocketMQ 的半消息 + 回查机制，把"本地事务 + 发消息"的原子性问题交给 MQ 解决，本质和本地消息表同源。

- SAGA：把长流程拆成一串本地事务，每一步配一个补偿动作，失败时逆序补偿；适合长链路业务，但不保证隔离性。

- 选型原则：能最终一致就不要强一致；多数互联网业务用"本地消息表/事务消息 + 幂等 + 对账兜底"就够了。

## 深度解析

- 底层原理：2PC 的根本缺陷是同步阻塞加协调者单点，参与者锁住资源干等指令，吞吐上不去；3PC 缓解了阻塞但仍有不一致窗口。

- 追问点：TCC 的空回滚（Try 没到 Cancel 先到）和悬挂（Cancel 之后 Try 才到）怎么处理？靠事务控制表记录状态并做检查。

- 追问点：消息投递是"至少一次"，下游必须做幂等，否则重试会造成重复消费——话题自然衔接接口幂等性设计。

- 常见误区：以为引入 Seata 等分布式事务框架就一劳永逸；最终一致是"重试 + 幂等 + 对账 + 监控"的整套体系，不是单个组件。

- 延伸：Seata 的 AT 模式通过数据源代理自动记录回滚日志，业务侵入小，但只适合基于关系型数据库的场景。
