## 问题

单体时代一个数据库自增主键就够了，服务拆分、分库分表之后，全局唯一的订单号怎么生成？
想听听你对几种主流方案的对比，以及实际选型时考虑哪些因素。

## 核心答案

- UUID：本地生成、无外部依赖，但 36 位太长且完全无序，
  做主键会导致 InnoDB 聚簇索引频繁页分裂，插入性能差。

- 数据库号段：每次从数据库批量申请一段号缓存在内存里，用完再取；DB 压力小，可用双 buffer 预取消除取号毛刺。

- 雪花算法：64 位 = 1 符号位 + 41 位时间戳 + 10 位机器位 + 12 位序列号，趋势递增、不依赖第三方存储、单机每毫秒 4096 个。

- 雪花的硬伤是时钟回拨：机器时间被回调后可能生成重复 ID，需要等待追平、报错降级或预留备用位等策略处理。

- Redis 自增：INCR 天然全局递增，实现简单，但强依赖 Redis 的可用性，还要考虑持久化丢号和单点性能上限。

- 选型考虑：趋势递增利于索引、长度影响存储和传输、外部依赖越多可用性风险越大；主流选择是雪花算法或号段模式。

## 深度解析

- 底层原理：InnoDB 主键即聚簇索引，无序 ID 插入位置随机，会引发页分裂和碎片；趋势递增的 ID 顺序追加，写入效率高。

- 追问点：41 位时间戳能用多久？毫秒级约 69 年；机器位不够时可以按机房、业务线拆分位，workerId 可由注册中心分配。

- 追问点：时钟回拨怎么办？小回拨等待追平，大回拨拒绝服务或切换备用 workerId，也有方案直接采用逻辑时钟。

- 常见误区：UUID 无序不代表不能用；做日志追踪号、业务流水号没问题，只是不适合当数据库聚簇主键。

- 延伸：美团 Leaf 同时落地了号段和雪花两种模式，百度 UidGenerator 对雪花位分配做了优化，可作为面试谈资。
