## 问题

用户网络超时后前端自动重试，结果订单创建了两个；MQ 也偶尔重复投递消息。
这类重复调用为什么无法彻底避免？接口的幂等性应该怎么设计？

## 核心答案

- 为什么需要幂等：网络重试、用户重复点击、MQ 至少一次投递、定时任务重跑都会让同一请求到达多次，
  重复执行会引发脏数据甚至资损。

- 唯一索引：对"创建类"操作用业务唯一键（如订单号）建唯一索引，重复插入直接报错回滚，最简单也最可靠。

- Token 机制：进入页面先领取唯一 token，提交时携带；服务端用 Redis setIfAbsent 或"删除 token"的原子操作保证只有第一次生效。

- 防重表：用请求唯一 ID 建去重表，处理前先插入，冲突即重复；插入与业务处理放在同一事务里保证原子性。

- 状态机/乐观锁：更新类操作用状态流转约束（只有"待支付"能变"已支付"）或带 version 的条件更新，天然幂等。

- 分层防重：前端防抖、按钮置灰挡住大多数误操作，但只是体验优化；真正的安全保证必须由后端幂等方案实现。

## 深度解析

- 底层原理：幂等的本质是"执行多次与执行一次结果相同"；
  天然幂等的有查询、按唯一键插入、条件更新（update ... where 状态=旧值）。

- 追问点：Token 校验为什么不能"先查再删"？并发下两个请求都能查到，必须用原子删除成功才执行，或加锁。

- 追问点：MQ 重复消费怎么办？消费完成后记录消息 ID（去重表/Redis），消费逻辑本身写成条件更新，双保险。

- 常见误区：把"前端禁用按钮"当成幂等方案；接口必须自我防御，前端只是第一层体验过滤。

- 延伸：分布式事务的消息投递是至少一次，所以幂等是最终一致性方案的必要配套，二者常被一起追问。
