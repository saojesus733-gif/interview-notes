## 问题

Python 的垃圾回收是怎么工作的？为什么循环引用能被回收、`__del__` 又会出问题？面试常拿它和 Java 的 GC 对比着问。

## 核心答案

**Python 的内存回收 = 引用计数（主）+ 分代回收（辅）**：

1. **引用计数**：每个对象记录被引用次数，降为 0 立即释放——实时性好，处理绝大多数场景；
2. **循环引用靠 gc 模块**：a.ref = b、b.ref = a 时计数永不为 0，`gc` 模块用**分代收集**（0/1/2 三代，新对象在 0 代，存活越久检查越少）定期扫描并回收不可达的循环组；
3. **`__del__` 的坑**：带 `__del__` 的循环引用对象在旧版本中无法被 gc 安全回收（释放顺序不确定），Python 3.4+（PEP 442）已能安全处理大多数情况，但依赖 `__del__` 释放资源本身就是反模式；
4. **正确姿势**：资源释放用上下文管理器（`with`）/ `finally` / `weakref` 解循环（父持子强引用、子持父弱引用）。

**排查手段**：`gc.collect()` 手动触发并看返回的不可达对象数；`gc.garbage` 查看无法回收的对象；`objgraph.show_backrefs()` 画引用链找成环点。

## 深度解析

- 与 Java GC 对比（面试常问）：Java 全靠分代追踪式 GC（后台线程，STW 与停顿调优是重点）；Python 以引用计数为主（即时释放、无 STW 大停顿），分代回收只兜底循环引用——所以 Java 的"Full GC 频繁"调优题在 Python 里对应的是"内存增长与循环引用"问题；
- 加分点：`gc.freeze()` 在 fork 前冻结对象减少 CoW 复制（多进程服务实用）；`gc.disable()` 常见于请求型服务的启动阶段优化（对象多时 gc 扫描贵），但要确保无循环引用泄漏；
- 雷区：以为 Python 有引用计数就"没有 GC 问题"——循环引用 + `__del__` + C 扩展三条路都能漏。
